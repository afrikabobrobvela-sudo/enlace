# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Qué es

Enlace es un LMS (estilo Brightspace) **en producción, con datos reales de estudiantes**, para docentes y alumnos de cualquier academia (nació en la Academia de Física de la BUAP). Responsable: Dr. Rodrigo Vela Vázquez. Todo lo que ven las personas usuarias (interfaz, mensajes de error de la API, correos) va **en español de México**; el código y sus comentarios también están en español. `LEEME.md` es la documentación para el responsable (despliegue, respaldos, novedades por versión): actualízala cuando cambie algo que él deba saber.

Producción: https://enlace.enlace-academia.workers.dev/ (cuenta de Cloudflare del responsable; en esta sesión no hay credenciales de Cloudflare, así que nunca se despliega desde aquí: se entrega el código y él publica con `npm run configurar`).

## Reglas de trabajo (del responsable)

- Nunca borrar ni reescribir tablas de D1 remoto sin respaldo y confirmación explícita. Las migraciones deben ser **no destructivas** (agregar tablas/columnas; copiar en vez de mover). `npm run db:migrate` y `npm run configurar` ya descargan un respaldo antes de migrar.
- Probar en local (`wrangler dev` con D1 local) antes de proponer un despliegue; cambios pequeños y verificables, y explicar cada despliegue.
- Secretos solo con `wrangler secret put` (`SESSION_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, opcional `RESEND_API_KEY`); en local van en `.dev.vars` (ignorado por git). El repositorio es público.
- D1 admite como máximo **5 términos por SELECT compuesto** (`UNION`); el adaptador de pruebas (`scripts/lib/d1-sqlite.mjs`) lo imita.
- Al agregar un `CHECK` o cambiar una columna existente en `db/schema.ts`, drizzle-kit genera una reconstrucción de la tabla (`__new_…`, `DROP TABLE`): **no la uses** (las llaves con `ON DELETE CASCADE` borrarían datos). Valida en el servidor y deja la migración solo con `ADD`.
- Plan gratuito de Cloudflare: máximo **50 consultas D1 por solicitud** (las pruebas lo vigilan con `store.counter.queries`), 100 parámetros por consulta (por eso las altas masivas usan `json_each(?)`), Worker ≤ 3 MB comprimido (`scripts/build.mjs` falla si se acerca), sin tiempo de CPU para procesar archivos grandes en el servidor (ZIP y compresión de fotos se hacen en el navegador).

## Comandos

```bash
npm install
npm test                         # compila la interfaz y corre todas las suites (≈18)
node scripts/build.mjs           # obligatorio antes de correr una suite suelta o wrangler dev
node scripts/test-papelera.mjs   # una sola suite (las de servidor usan SQLite en memoria vía node:sqlite)
npm run dev                      # build + wrangler dev en http://localhost:8787 (requiere .dev.vars)
npm run db:migrate:local         # migraciones en la D1 local de wrangler dev
npx drizzle-kit generate --name <nombre>   # nueva migración a partir de db/schema.ts (revisa el SQL)
```

No hay linter ni TypeScript en tiempo de ejecución (`db/schema.ts` solo documenta el esquema para drizzle-kit). CI (`.github/workflows/pruebas.yml`) corre `npm install && npm test` en cada push.

Para `wrangler dev` sin tocar el `wrangler.toml` versionado: sustituye temporalmente `PEGA_AQUI_EL_ID_DE_TU_BASE` por cualquier UUID y restáuralo al terminar (nunca subas un `database_id` real ni el correo real). Para entrar sin Google en local, inserta un usuario y una fila en `aula_logins` en la D1 local y firma una cookie `__Host-enlace_session` con `signToken({ uid, sid, ver, exp }, SESSION_SECRET)` de `src/server/http.js`; en Chromium se puede fijar con `document.cookie` sobre `http://localhost:8787` (el prefijo `__Host-` exige contexto seguro; localhost lo es).

## Arquitectura

- **Un solo Worker** (`src/worker.js`): `/api/*` → `src/server/api.js`, `/auth/*` → `src/server/auth.js`, todo lo demás se sirve desde `src/generated/assets.js`, que `scripts/build.mjs` genera incrustando `src/public/` (no se edita a mano; está en `.gitignore`). No hay framework ni empaquetador en el frontend: scripts clásicos con `defer`, en el orden de `src/public/index.html`, que comparten globales (`current`, `me`, `section`, `request()`, `esc()`, `modal()`, `render()`…). Un archivo nuevo de `src/public/` debe agregarse a `index.html` **y** a los `vm.runInContext`/`browser.load` de las pruebas de interfaz que cargan los scripts a mano.
- **Rutas de la API**: mapas `'MÉTODO /ruta': handler(ctx)` en `api.js`, `attendance.js`, `grading.js`, `directory.js`, `privacy.js`, `periods.js`, `dashboard.js`, `reports.js`, `demo.js`, `backup.js` y `users.js` (se buscan en ese orden en `api()`); `api()` resuelve la identidad, exige mismo origen + cabecera `X-Aula-Request: 1` en todo lo que no sea GET (CSRF), y convierte `fail(mensaje, status)` en JSON `{ error }`. Validación y helpers de D1 (`one`, `all`, `run`, `text`, `email`, `readJson`) en `http.js`. Antes de cualquier escritura, `assertWritable()` (`periods.js`) rechaza con 409 los cursos archivados (lee `course` de la URL o de una copia del cuerpo). `/api/me` incluye `privacyAccepted`; sin aceptar el aviso (`PRIVACY_VERSION`) la interfaz no muestra nada más.
- **Identidad**: cookie firmada con HMAC que lleva `uid`, `sid` y `ver`; `identity()` exige una fila vigente en `aula_logins` (sesión revocable por dispositivo) y que `ver` coincida con `aula_users.session_version` (subirla cierra todas las sesiones). Acceso con Google (OIDC) y con Microsoft Entra (OIDC, solo el tenant fijo `MICROSOFT_TENANT_ID`, identidad `tid:oid`, correo de `preferred_username` limitado a `MICROSOFT_EMAIL_DOMAINS`); el enlace por correo solo se activa con Resend y dominio propio. Las cabeceras `oai-*` de ChatGPT Sites (versión 8) se ignoran a propósito.
- **Roles**: globales `admin` / `teacher` / `student`; la fuente de verdad es `AULA_OWNER_EMAIL` (cuenta principal, en `wrangler.toml`) más la tabla `aula_teachers`, y se relee en cada solicitud. Por curso, `access()` en `access.js` decide `teach` (admin, propietario que **siga siendo docente** — `ownsCourse` — o miembro con rol `teacher`) y bloquea a miembros `removed` y cursos en `aula_deleted_courses`. Toda ruta que recibe `course` debe pasar por `access()` y, si modifica, por `requireTeacher()`; los registros se buscan siempre con `id=? AND course=?`.
- **Datos**: dos generaciones conviven.
  - `aula_records` guarda como JSON en `data` las unidades, materiales, noticias, foros, publicaciones, equipos y evaluaciones (`kind`); control de concurrencia con `revision` (409 si cambió).
  - Actividades, entregas, calificaciones, ponderaciones, categorías, rúbricas, intentos y asistencia están en tablas normalizadas con CHECK y llaves foráneas (`aula_tasks`, `aula_submissions`, …); `gradebook.js` las devuelve al frontend con la forma de registro `{ id, kind, data, revision }` de la versión 8, así el frontend trata todo como `current.records`.
  - Papelera: `deleted_at` en `aula_records` y `aula_tasks`; **cualquier consulta nueva sobre esas tablas debe filtrar `deleted_at IS NULL`** (y las entregas, por actividad no eliminada).
  - `GET /api/course` entrega todo el curso en una sola respuesta, ya filtrado por rol (el alumno no recibe respuestas correctas, borradores de calificación, correos/matrículas ajenas ni archivos que no puede ver).
- **Vista como alumno**: `?as=student` en `GET /api/course` y `GET /api/attendance` (`viewAs()` en `access.js`, asíncrona) hace que quien enseña reciba los datos con los filtros de alumno (`viewer` null: sin entregas propias). `?as=m:<id de inscripción>` da lo que ve ESE alumno (`member`; `courseGradebook` filtra por `memberId`, los intentos por `attemptUser`, que es `demo:<id>` para alumnos sin cuenta) y `viewAudit()` lo registra en `aula_audit`; la respuesta trae `viewing`. En el frontend, `previewAsStudent`/`previewMember` agregan el parámetro (`viewSuffix()`) y `request()` rechaza cualquier escritura mientras están activos; las pantallas de alumno identifican a "su" alumno con `myMember()` y `viewerKey()`, nunca con `me.id`.
- **Usuarios** (`users.js`, `src/public/usuarios.js`, solo admin): búsqueda paginada, ficha, suspender (`aula_users.suspended_at`; `identity()` y los regresos de acceso lo rechazan), transferir curso y registro (`aula_audit`, escrito con `auditStatement()` en el mismo batch).
- **Registro de docentes** (`src/server/directory.js`, `src/public/registro.js`): catálogo de academias y unidades académicas (lo edita la administración), solicitudes para ser docente (solo correos de `TEACHER_EMAIL_DOMAINS`, por omisión `correo.buap.mx`) que la administración aprueba o rechaza, y `academy_id`/`unit_id` en `aula_users` y `aula_courses`. `/api/me` incluye el estado del registro (`needsClassification`, `canRequestTeacher`, `teacherRequest`, `pendingTeacherRequests`).
- **Archivos**: R2 con id aleatorio; metadatos en `aula_files` (`scope` material/entrega). La descarga (`downloadFile`) verifica que el archivo esté enlazado desde una unidad/material/actividad visible y no eliminada, o sea del propio alumno o de su equipo. La vista previa (`?preview=1`) detecta el tipo real por los primeros bytes y sirve con `sandbox`. Cuotas: 300 MB por alumno y curso, 9 GB en total.
- **Periodos y co-docentes** (`periods.js`): `POST /api/course/copy` copia contenido, actividades y reglas reasignando ids dentro del JSON con `remap()`; las filas de `aula_files` copiadas apuntan al objeto original con `r2_key` (usa siempre `r2_key || id` para leer o borrar en R2). Co-docente = fila de `aula_members` con `role='teacher'`, que solo cuenta mientras la persona siga siendo docente.
- **Prórrogas** (`aula_extensions`): `withExtension()` en `gradebook.js`; el alumno recibe la actividad ya con su fecha (`data.extended`) y los docentes reciben registros `kind:'extension'`. En el frontend, `dueFor()` y `computeGrade`/`riskReport` reciben la fecha por alumno.
- **Publicación programada** (`published.js`): `data.publishAt` en unidades, materiales, noticias, foros y evaluaciones; para el alumno un registro existe solo si `isPublished()` (visible y fecha cumplida). Toda consulta o comprobación de "lo que ve un alumno" sobre `aula_records` debe usar `isPublished()`/`publishedSql()` (curso, descargas, foros, evaluaciones, avisos, seguimiento). En avisos, la fecha es `max(updated, publishAt)`.
- **Seguimiento del contenido** (`aula_progress`, `POST /api/progress`, ayudantes en `workspace.js`): abierto/completado por alumno y material; `GET /api/course` lo incluye en `progress` (todos para quien enseña, solo el propio para el alumno o la vista de un alumno).
- **Evaluaciones en la calificación**: `data.grade = { category, points, policy }` (solo categorías de actividades del curso, validado en el servidor); en `grading.js`, `countedQuizzes()` y `quizScore()` (mejor/último/promedio) alimentan `computeGrade()`; sin intento no cuenta.
- **Evaluaciones** (`quizzes.js`, `src/public/evaluaciones.js`): `evaluate()` es un analizador propio (nunca `eval`); `quizInstance(quiz, usuario, intento)` genera valores y orden con semilla determinista; `aula_attempt_starts` fija el inicio para el tiempo límite; al alumno solo le llega `publicQuestions()`.
- **Inicio, avisos, calendario y comprobantes** (`dashboard.js`, `src/public/pendientes.js`, `src/public/calendario.js`): los avisos se calculan de lo publicado (no hay tabla de avisos); uno es nuevo si es posterior a `aula_users.notices_seen_at` («marcar todo», que vacía `aula_notice_reads`) y su clave `tipo:id:fecha` no está en `aula_notice_reads` (leídos uno por uno). `GET /api/calendar?from&to` (máx. 100 días) junta actividades (con prórroga y estado para el alumno) y sesiones de todos los cursos activos; `homeView` `calendar` y `avisos` son para todos (las demás vistas de inicio, solo admin). **Historial de calificaciones** (`aula_grade_history`): lo escriben `saveGrade` (en el mismo `batch`, condicionado a que se guardara), la publicación en bloque y una nueva entrega. **Reportes y limpieza de R2** (`reports.js`, en `admin-tools.js`): solo administración; los huérfanos no filtran `deleted_at` a propósito (la papelera se puede restaurar).
- **Asistencia con código** (`attendance.js`, `checkin.js`): `checkin_mode` 'qr' o 'code'. En modo código, `locationCheck()` compara la ubicación del alumno con la del docente (guardada solo mientras el registro está abierto) y la red (`networkOf`, prefijo de IP); guarda solo distancia, precisión y `flag` en `aula_checkins`, y la nota de asistencia lleva «· Por revisar: motivo» hasta que el docente la confirma.
- **Modo examen** (`settings.exam` de la evaluación; `publicSettings()` quita contraseña y salón al alumno): `POST /api/attempt/start` pide la contraseña solo al crear el intento (`aula_exam_tries` bloquea a las 10) y marca la ubicación; `POST /api/attempt/progress` guarda respuestas, posición y eventos en `aula_attempt_starts`; con `noBack`, `finalAnswers()` y el guardado mantienen fijas las respuestas ya dejadas atrás; al enviar, `integritySummary()` se copia a `aula_attempts.integrity`. **Bloqueo al salir** (`exam.lockOnLeave`, `lockGrace`): el navegador llama `POST /api/attempt/away` (keepalive) al ocultarse y `/back` al volver; `applyLock()` bloquea en `aula_attempt_starts` (`locked_at`, `unlock_code` de 6 cifras que solo sale en `GET /api/exam/monitor`) si pasó la tolerancia, también al retomar en `/start`; bloqueado, `progress` y el envío responden 423; `/api/attempt/unlock` (5 intentos) y `/api/exam/resume` (docente) desbloquean. En el navegador, `showExamLock()` en `evaluaciones.js`. En el navegador, `startExam()`/`stopExam()` en `evaluaciones.js` (clase `exam-running` en `body`). **Examen estricto (12.16)**: `identity()` calcula `activeExam` (examen con `exam.lockPlatform` empezado, sin enviar y en tiempo) y `assertExamRoute()` en `api()` solo deja pasar `EXAM_ROUTES`, `GET /api/course` de ese curso (reducido, `examOnly`) y las imágenes de ese examen (423 con `activeExam` para lo demás; el frontend llama `goToActiveExam()`). El intento guarda `session_id`: retomarlo desde otra sesión lo bloquea y lo reasigna (`claimDevice`), y la sesión anterior recibe 409 `otherDevice` (`assertDevice`). Las preguntas pueden llevar `image` (id de archivo de material); `shuffleOptions` agrega `perm` a la instancia (nunca llega al alumno); `opensAt`/`closesAt`/`timerMode:'fixed'` en `deadlineOf()`/`assertOpen()`; `settings.results` (`score`, `review`, `releaseAt`: antes de esa fecha nada) y `studentAttemptView()` deciden qué ve el alumno. Capturas: marca de agua y detección de teclas en el navegador (evento `capture` en la integridad).
- **Banco de preguntas y preguntas al azar (12.17)** (`bank.js`, `src/public/banco.js`, sección `bank`): `aula_question_bank` guarda la pregunta con la forma de `questionFields()` (sin `pool`), por dueño y tema; `shared=1` la muestra a docentes de la misma `academy_id`; `fingerprint` evita duplicados. `POST /api/bank/use` devuelve copias con el tema como `pool` y, si la imagen es de otro curso, crea una fila de `aula_files` en el curso destino con el mismo `r2_key`. Las imágenes del banco se descargan con `?bank=1` (`bankImageVisible`). `settings.draw = [{pool, count}]`: `quizInstance()` sortea al final (no cambia instancias viejas), el total es `instance.length` y `questionCount()` da cuántas recibe cada alumno. El alumno recibe `questions` con `null` en las que no ha contestado (solo `questionCount`); cualquier pantalla de alumno debe tolerar esos `null`. `ORPHANS` en `reports.js` cuenta las imágenes de preguntas (evaluaciones y banco) y ya usa los 5 términos que admite D1.
- **Secciones (12.18)** (`sections.js`, `src/public/secciones.js`): `aula_sections` por curso; `aula_members.section` y `aula_sessions.section` ('' = sin sección / todo el curso); `aula_section_dates` (item, section, start_at, due, end_at) da fechas por sección a actividades y evaluaciones. Fecha efectiva del alumno = prórroga ?? sección ?? general: `withSectionDates()` en `courseGradebook`/`saveSubmission`, joins en `dashboard.js` (pendientes y calendario), `quizForStudent()` en `attemptContext()` (evaluaciones), el SQL de `activeExam` en `identity()` y el monitor. `GET /api/course` trae `sections` y, para quien enseña, `sectionDates` (una sola consulta). En el frontend, `studentsInView()`/`sessionsInView()`/`sectionFilterHtml()` aplican el filtro (localStorage por curso) y `dueFor()` usa `sectionDateOf()`; cualquier lista nueva de alumnos para el docente debe usar `studentsInView()`. Asistencia: una clase de sección solo acepta marcas y registros de sus alumnos (`sessionApplies()`). **Contenido por sección**: `data.sections` (aula_records de unidades, materiales, noticias, foros y evaluaciones) y la columna `aula_tasks.sections` (JSON; '' = todas), validadas con `sectionsField()`. Toda comprobación de «lo que ve un alumno» debe sumar `forSection()`/`sectionSql()` (`published.js`) a `isPublished()`/`publishedSql()`: curso, descargas, entregas, foros, `quizForStudent()`, seguimiento, avisos, pendientes y calendario. En el frontend, `itemApplies(record, member)` decide si una actividad o evaluación cuenta para un alumno (`studentGrade`, libro, riesgo, envíos) y el filtro es de varias secciones (`selectedSections()`); los editores obtienen el selector por `visible(…, sections)` y `save()` lo lee solo.
- **Foto de perfil (12.18)** (`photos.js`, `src/public/foto.js`): `aula_users.photo` (llave de R2 `perfil/<usuario>/<uuid>.<ext>`) y `photo_updated` (versión en la URL `/api/photo/<usuario>?v=`). La ven la persona, la administración y quien comparte curso con ella si una de las dos enseña. Con `FOTO_OBLIGATORIA="1"` (wrangler.toml), `assertHasPhoto()` en `api()` responde 428 `{needsPhoto}` a un alumno sin foto (salvo `PHOTO_FREE_ROUTES` y un examen activo) y la interfaz muestra `renderPhotoGate()` (cámara con getUserMedia; si no, `<input capture>`). Las pruebas no fijan la variable (solo `test-foto.mjs`).
- **Avisos por correo (12.19)** (`mail.js`, `digest.js`): `sendMails()` nunca lanza. Envía por Gmail SMTP (`cloudflare:sockets`, `smtp.gmail.com:465`, secretos `CORREO_AVISOS` + `GMAIL_APP_PASSWORD`) o por Resend si hay `RESEND_API_KEY` + `EMAIL_FROM`, y cuenta por día en `aula_mail_log` (tope `MAIL_DAILY_LIMIT`, 450). En las pruebas se usa `env.MAILER` (cartero en memoria) o `env.SMTP_CONNECT` (Gmail simulado). El resumen diario lo corre `scheduled` en `worker.js` (cron en `wrangler.toml`) con `runDigest()`: son 7 consultas para todos (la 7.ª, foros), con ventana por persona `aula_users.digest_sent_at` (máx. 3 días), y solo avanza la ventana de quien sí recibió su correo. `email_digest=0` lo apaga («Mi perfil»). La noticia urgente (`POST /api/notice/email`) guarda `data.emailedAt`, que se conserva al editarla. Cualquier consulta nueva del resumen debe respetar `publishedSql()`/`sectionSql()` como la campana. `ENLACE_URL` (secreto) es la dirección del botón de los correos; `npm run correo` configura todo.
- **Accesos (12.20)** (`accesos.js`, `renderAccess()` en `app.js`, sección `access`): `aula_login_log` guarda cada inicio de sesión (lo escribe `sessionCookie()`; `aula_logins` solo conserva las vigentes) y `aula_course_access` los ingresos por curso. `recordVisit()` en `GET /api/course` es un solo upsert: visita nueva tras 30 min y sin escritura si pasaron < 5 min. Solo cuentan quienes `access()` marca como `visitor`: propietario, co-docente o alumno; la administración no cuenta. `GET /api/course/access` (quien enseña) cuenta los inicios entre `created` y `archived_at` del curso. **Código por sección**: `aula_section_dates.code` (solo evaluaciones). `quizWithSectionDates()` lo pone en `settings.startCode`; `startCodeOf()` (código de la sección ?? contraseña del examen) se pide en `/api/attempt/start`; `publicSettings()` lo quita y deja `needsCode`. `sectionDates` de `GET /api/course` lleva el código solo para quien enseña. En el editor, `quizSectionsHtml()`/`readQuizSections()`/`readQuizSectionDates()` (`secciones.js`) reemplazan al selector genérico (`visible(…, [], false)`).
- **Tipos de reactivos (12.21)** (`src/server/reactivos.js`, `src/public/reactivos.js`, cargado antes de `evaluaciones.js`): además de `choice` y `numeric` («Aritmética»), `NEW_TYPES` = `truefalse`, `multi`, `fill` (espacios `[[resp|alt]]` en el enunciado), `matching` (`pairs`, `extra`), `ordering`, `essay`, `short`, `multishort` y `sigfig`. Cada tipo tiene `validateNew`, `instanceNew`, `gradeNew` y `publicNew`. `instanceNew` usa un generador propio por pregunta, para no cambiar las instancias de evaluaciones viejas, y guarda lo privado en `key` (se quita junto con `perm`/`values` antes de enviar al navegador). La calificación es por crédito (0 a 1) por pregunta: `scoreOf(details)` da `correct` (créditos completos), `score` y `pending` (respuestas escritas sin revisar, que cuentan 0). `POST /api/attempt/review` (docente) pone `credit`/`feedback`/`reviewed` en `details` y recalcula `score`. `attemptRecord()` agrega `pending`. Con `results.review='none'`, `studentAttemptView()` deja solo `feedback`. `cleanSaved()` valida lo que guarda `/api/attempt/progress`. En el navegador, `newAnswerInputHtml`/`collectNewAnswer`/`restoreNewAnswer` usan los nombres `q_<índice>` o `q_<índice>_<k>`.
- **Acceso especial (12.22)** (`especial.js` en servidor y navegador): actividades en `aula_extensions` (ahora con `start_at`; «prórroga» = acceso especial de un alumno) y evaluaciones en `aula_quiz_access` (start_at, end_at, extra_minutes, extra_attempts). «Solo con acceso especial»: `aula_tasks.special_only` y `data.specialOnly` en la evaluación (se conserva al editarla y `periods.js` no lo copia). **Toda consulta de «lo que ve un alumno» sobre actividades o evaluaciones debe sumar `specialTaskSql()`/`specialRecordSql()` (`published.js`)** a la de sección: `courseGradebook`, `saveSubmission`, descargas, `dashboard.js` (pendientes, avisos, calendario) y `digest.js`. Evaluación efectiva del alumno = general → sección → acceso especial: `quizWithAccess()` después de `quizWithSectionDates()` en `quizForStudent()`, `GET /api/course` (las filas van en la misma consulta que las secciones: `quizAccess` para quien enseña) y el monitor. El SQL de `activeExam` en `identity()` también suma `qa.extra_minutes` y el horario propio. En las fechas con `nullif(e.due,'')` (una fila puede no tener vencimiento). En el navegador: `itemApplies()` usa `hasSpecialAccess()`; `extensionOf()` e `indexed()` (`app.js`) indexan los registros una vez por carga.
- **Fechas (12.22)** (`src/public/fecha.js`, cargado primero): un `MutationObserver` envuelve cada `input[type=datetime-local|date|time]` en `.dt-field` con un botón y un calendario propio; el campo nativo queda oculto en el formulario con su valor de siempre (se lee igual con `FormData`) y su propiedad `value` actualiza el botón. En pruebas con Playwright, llena esos campos con `evaluate` (el nativo no es visible) o usando el selector. **Interfaz en caché**: `scripts/build.mjs` calcula un `etag` por archivo y `worker.js` responde 304 con `If-None-Match` (`Cache-Control: no-cache`; `vendor/` sigue `immutable`). **Botones**: nada usa `transform` en `:hover`/`:active` (la auditoría con estados forzados detectaba que se movían); los estados se marcan con color y sombra.
- **Evaluaciones 12.23** (`quizzes.js`, `resultados.js`, `importar.js`, `oficina.js`): `points`, `explanation` y `optionFeedback` por pregunta (`extraFields()`); `scoreOf(details, questions)` pondera por puntos.
